# Recipes

Generated by okf-check 0.3.0 (ruleset 49f891584e77). Do not edit: regenerate with okf-check skill --no-profile.

## Recipe: add a document

1. Read the documents already in the directory you will add to and copy their frontmatter shape: the same keys, and the same `type` word for the same kind of document. Name the file in lowercase with hyphens, ending in `.md`, and make sure no other document has the same file name stem.
2. Create the document. Its frontmatter carries the provenance, in exactly this shape:

   ```
   ---
   type: <same type as the sibling documents>
   title: <Title>
   description: <one sentence>
   status: stable
   verified:
     - {by: agent:okf-agent, at: YYYY-MM-DD}
   sources:
     - {title: "Issue #<n>", resource: <issue URL>}
   ---
   ```

   `YYYY-MM-DD` is the date of this run. `<n>` and `<issue URL>` are the issue's number and address exactly as the snapshot states them. Add one more `sources` entry for each attachment you used, with its file name as `title` and its address as `resource`. Every `verified` entry is a `{by, at}` mapping: a plain string entry is an error. With the runbook profile on, do not use the issue URL as a source; follow `references/profile.md` instead.
3. Add the document's entry line to the `index.md` of the SAME directory, in this form:

   ```
   * [Title](file.md) - description
   ```

   `file.md` is the new file's name relative to that `index.md`. When the directory has no `index.md`, create one that lists its documents; an index file needs no frontmatter, except under the runbook profile, where `references/profile.md` names what a new index must carry.
4. Run the self-check (see the check recipe) and fix every error.

## Recipe: update a document

1. Edit the existing file in place. Keep its path and its file name.
2. Append a fresh entry to its `verified` list and keep every earlier entry:

   ```
   verified:
     - {by: agent:okf-agent, at: YYYY-MM-DD}
   ```

   `YYYY-MM-DD` is the date of this run.
3. Refresh `sources`: add the entry for this issue (and one for each attachment you used) and keep the earlier entries that still support the text. The entry shape is the one in the add recipe.
4. Never touch an existing `human:` entry, `reviewed_at` or `reviewed_hash`. Changing the body of a human-reviewed document makes its review stale; the check reports that as a `stamp-stale` warning and a maintainer redoes the review.
5. When you change the title or the description, update the document's line in its directory's `index.md` to match.
6. Run the self-check (see the check recipe) and fix every error.

## Recipe: retire a document

A document is retired in place. Files are never deleted or renamed: a document that exists at the base branch and is missing from the bundle is an `immutability` error, and the pipeline refuses a delete or a rename.

1. Open the existing file and set `status: deprecated` in its frontmatter, adding the key when it is absent.
2. Begin the body with one short line starting `Deprecated:` that gives the reason and names the document that replaces it, when there is one.
3. Keep the file at its path and keep its line in the directory's `index.md`.
4. When the retired content needs a replacement, add the replacement as a new document under its own name (see the add recipe) and point to it from the retired one.
5. Append an agent entry to `verified` as in the update recipe, then run the self-check (see the check recipe).

## Recipe: run the self-check

- The okf-agent runs `okf-agent-check` with no arguments. It checks the bundle against the default branch and reports the findings document that the next recipe describes.
- A maintainer runs the engine directly: `okf-check check <bundle_root> --base origin/<default branch> --format json`, with `<bundle_root>` from `.okf/publish.toml`.
- The exit code tells whether a check ran: `0` the bundle passed (warnings are allowed), `1` the bundle was refused (at least one error), `2` no check completed because of a usage, configuration or file error.
- Fix every error before you finish. Fix warnings too: a warning such as `index-line-missing` means a document is not listed in its directory's `index.md`, and the add recipe says how to list it.
- When an error remains after your fixes, do not open a pull request; report which rule fired and on which document.

## Recipe: read findings.json

The check's findings document is JSON, schema version 1. Read these fields in this order:

1. `result` is `pass` or `fail`. `headline` says the same in one line.
2. `repo_findings` and `profile_findings` are lists of `{rule, severity, doc, message}`: the rule's name without its `repo.` or `profile.` prefix, `error` or `warning`, the document it is about, and what to change. `references/rules.md` explains every rule. `profile_findings` stays empty unless the runbook profile is on.
3. `admin` is the platform build's own verdict: `verdict` is `pass`, `refuse`, `blocked` or `error`, and `report.causes` lists each cause with its `code`, `title` and `hint`. `references/findings.md` explains every code.
4. `not_checked` lists what this check cannot see, such as the rules that need `--base`. A rule listed there did not run; a green result does not cover it.

Only an `error` finding makes `result` `fail`.
