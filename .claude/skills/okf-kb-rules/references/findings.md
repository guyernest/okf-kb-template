# Findings

Generated by okf-check 0.3.0 (ruleset 49f891584e77). Do not edit: regenerate with okf-check skill --no-profile.

## Exit codes

| Code | Meaning |
|------|---------|
| `0` | a check completed and passed; warnings are allowed |
| `1` | a check completed and the bundle is refused or failed: at least one error |
| `2` | no check completed (usage, configuration, file or harness error); no findings document exists |

## findings.json, schema version 1

| Field | Meaning |
|-------|---------|
| `schemaVersion` | the document's schema version, `1` |
| `result` | `pass` or `fail`; only an `error` finding makes it `fail` |
| `headline` | the verdict in one line |
| `repo_findings` | repository rules: a list of `{rule, severity, doc, message}` |
| `profile_findings` | runbook profile rules, same shape; empty unless the profile is on |
| `admin` | the platform build's verdict (`verdict` is `pass`, `refuse`, `blocked` or `error`) and its `report.causes` |
| `not_checked` | a list of `{id, message}`: what this check cannot see, such as rules that need `--base` |

In a finding, `rule` is the rule's name, `severity` is `error` or `warning`, `doc` is the document it is about and `message` says what to change.

## Platform build codes (guidance version 1)

Each `admin.report.causes` entry carries one of these codes with its `title` and `hint`. In a title or hint, `{doc}` stands for the document and `{target}` for the link or name the finding is about.

| Code | Title | Hint |
|------|-------|------|
| `ambiguous_join_name` | “{target}” does not name exactly one table | Rename the join file (and its title and links) so each half names exactly one table, for example {candidates_sample}. If “{target}” really is one table, give it a single document named {target}.md. |
| `dangling_edge_dropped` | A relationship was left out because “{target}” is not in the bundle | Check the reference in {doc}. Either add the missing document “{target}” or correct the reference so it names an existing one. |
| `duplicate_entity_id` | Two documents would receive the same identifier “{target}” | Rename one of the documents so its file name is unique across the bundle. The documents sharing this identifier are {candidates_sample}. |
| `frontmatter_missing` | A document has no metadata block | Add a metadata block at the very top of {doc}: a line containing only ---, the fields (including a type), then a closing line containing only ---. |
| `frontmatter_parse_error` | A document's metadata block is not valid YAML | Open {doc} and correct the metadata block. Common causes are indentation, a missing colon, or a value containing a colon that needs quotes around it. |
| `frontmatter_too_large` | A document's metadata block is too large | Shorten the metadata block in {doc}. Long text belongs in the body of the document, below the closing ---. |
| `link_target_missing` | A link points to a page the bundle does not contain | Either add the page “{target}” to the bundle, or change the link in {doc} so it points at a page that exists. |
| `missing_join_on` | A join note has no SQL join condition | Add the join condition inside a SQL code block, on a line that starts with ON (for example ON a.id = b.a_id). Until then the join stays out of the graph. |
| `missing_type` | A document has no type | Add a type line to the metadata block of {doc}, for example type: Table, using a type the bundle already uses elsewhere. |
| `unresolved_join_name` | “{target}” does not name any table | Check the spelling of “{target}” in the join file name, or add the missing table to the bundle. If the join is no longer needed, remove its join note. |
